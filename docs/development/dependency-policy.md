# dMeM 依赖准入策略

## 1. 原则

- 优先使用 Go 标准库，但不追求零依赖。
- 每个依赖必须有明确用途、许可证和维护状态。
- 依赖不得改变领域模型、权威数据边界和降级语义。
- 核心功能不得强制要求独立数据库、消息队列、搜索服务或常驻辅助进程。
- 依赖默认不得联网、上传遥测、下载模型或检查更新。

## 2. SQLite 与 CGO

允许使用 CGO SQLite 驱动，优先评估成熟、广泛使用并能控制 SQLite 编译能力的驱动。

要求：

- 项目只采用一个 SQLite 驱动。
- 构建环境包含受支持的 C 工具链。
- 发布流程明确支持的 Linux 架构和 libc 组合。
- 测试与发布使用相同驱动和 SQLite 编译选项。
- SQLite 连接、PRAGMA 和生命周期由 storage 模块集中管理。
- repository 之外不得自行打开 SQLite 连接。

允许 CGO 意味着交叉编译和发布矩阵更复杂，不承诺未经构建验证的平台兼容性。

## 3. ORM

允许使用 ORM，但仅限：

- repository 内部的持久化模型映射。
- 普通常规 CRUD。
- 简单条件查询。
- 明确短事务内的记录操作。

以下操作使用显式 SQL：

- 首版 schema 初始化。
- FTS 虚拟表和全文查询。
- 幂等写入和条件版本更新。
- 任务原子领取。
- SQLite PRAGMA、完整性检查和一致性备份。
- 索引创建、重建和复杂批处理。
- 性能敏感或需要精确 SQL 语义的查询。

边界：

```text
领域对象
  → 显式转换
  → persistence model
  → ORM 或显式 SQL
  → SQLite
```

禁止：

- 将 ORM model 同时作为 API model 或领域对象。
- 在接口层直接操作 ORM handle。
- 使用 ORM hook 实现状态机、证据绑定或冲突规则。
- 依赖 lazy loading。
- 使用 ORM 自动迁移创建或修改正式 schema。
- 让 ORM 隐式事务替代应用层定义的事务边界。

ORM 候选必须通过 SQLite 事务、批量写入、条件更新、自定义类型、JSON 元数据和 FTS 共存验证后才能采用。

## 4. 第一阶段 Schema 策略

第一阶段不实现 SQLite schema migration：

- 新数据库通过一份版本化初始化 SQL 创建完整 schema。
- 数据库保存单一 `schema_version`。
- daemon 打开已有数据库时只校验版本是否完全匹配。
- 版本不匹配时拒绝普通启动并返回 `incompatible_version`。
- 不使用 ORM AutoMigrate，也不在启动时自动修改已有表。
- 开发阶段发生不兼容 schema 变化时，使用新数据库重新初始化；需要保留的数据通过明确的导出和导入处理。

正式 schema migration 属于后续阶段，届时通过独立 ADR 和设计文档引入。

## 5. 本地服务协议

第一阶段采用 HTTP/JSON over Unix Domain Socket：

- 服务端优先使用 `net`、`net/http` 和 `encoding/json`。
- 第一阶段不引入 Web 框架或 RPC 框架。
- MCP、Agent 插件等作为外部适配器，不作为唯一核心协议。
- 后续只有在出现明确的多语言强类型或流式需求时才评估 gRPC。

## 6. 依赖注入

不引入依赖注入框架或全局 service locator。使用接口、显式构造函数和启动装配函数管理依赖与生命周期。

## 7. 代码生成

允许代码生成，但必须满足：

- 生成器版本固定。
- 生成命令可重复并进入项目文档或构建脚本。
- 生成过程默认不联网。
- CI 能检查生成结果是否最新。
- 生成代码不得绕过领域层和 repository 边界。

适合生成 API 客户端、Mock 和静态协议类型，不使用生成器隐藏核心状态机和事务规则。

## 8. SQLite 扩展

采用白名单策略。

第一阶段允许：

- 项目编译时明确启用的 SQLite 官方能力。
- FTS、JSON、备份和完整性检查能力。

后续可评估版本固定、许可证兼容、可重建的嵌入式向量扩展。

禁止：

- 通过 API 或配置加载任意动态库路径。
- 运行时从网络下载 SQLite 扩展。
- 未经审核调用任意 `load_extension`。
- 将扩展内部索引格式作为唯一权威数据。

## 9. 向量检索

```text
第一阶段：SQLite 结构化过滤 + FTS 关键词检索
第二阶段：评估 SQLite 内嵌向量索引
后续阶段：实体和关系增强
```

向量方案必须记录 `memory_id`、`revision_id`、嵌入模型、维度和索引版本，支持完整重建，并在不可用时降级为关键词检索。

## 10. 联网与遥测

禁止依赖在未显式配置时：

- 上传使用数据、错误内容或请求参数。
- 自动检查更新或下载模型。
- 自动发现网络服务。
- 自动读取云环境凭据并连接托管平台。
- 将 SQL 参数、原始事件或记忆内容发送到外部追踪服务。

允许联网的客户端必须支持超时、取消、完全关闭遥测和明确的数据外发策略。

## 11. 许可证

默认允许：

```text
Apache-2.0
MIT
BSD-2-Clause
BSD-3-Clause
ISC
0BSD
```

以下许可证需要逐项审查，不作为默认依赖引入：

```text

LGPL
GPL
AGPL
SSPL
BSL
Elastic License
Commons Clause
其他 source-available 许可证
```

审查范围包括直接依赖、传递依赖、嵌入 C 代码、SQLite 扩展、模型、tokenizer 和代码生成模板。本策略不替代正式法律意见。

## 12. 维护与安全

依赖准入要求：

- 仓库未归档且维护状态可识别。
- 有可追踪版本或提交。
- 支持项目采用的 Go 版本。
- 许可证明确。
- 不依赖未声明的系统服务。
- 已知高危漏洞有升级或缓解方案。
- 失败、取消、超时和资源行为可控。

依赖通过 Go modules 管理，提交 `go.mod` 和 `go.sum`，不从浮动分支构建发布版本。依赖更新必须检查实际变更、许可证和安全公告，并执行 Go 漏洞检查。

## 13. 第一阶段基线

```text
SQLite：允许 CGO，采用一个成熟驱动
ORM：允许，只用于 repository 和普通 CRUD
Schema：初始化 SQL + 精确版本校验，不实现 migration
接口：标准库 HTTP/JSON over Unix Domain Socket
日志：Go 标准库结构化日志
依赖注入：显式构造，不使用框架
关键词检索：SQLite FTS
向量检索：第二阶段评估
遥测：默认关闭
外部服务：全部可选
```
